## Design requirements

| Requirement | Status | Evidence and notes |
| --- | --- | --- |
| Abstraction, encapsulation and information hiding used where appropriate | `Met` | Model classes keep state private and expose it through methods, for example `src/main/java/com/hospitalclaims/model/Patient.java:4-12` and `src/main/java/com/hospitalclaims/model/Claim.java:6-15`. Repository connection handling is hidden behind `RepositorySupport` in `src/main/java/com/hospitalclaims/repository/RepositorySupport.java:8-20`. |
| Inheritance used | `Met` | Repository classes inherit shared behavior from `RepositorySupport`, for example `ClaimRepository extends RepositorySupport` in `src/main/java/com/hospitalclaims/repository/ClaimRepository.java:14-17`. Exception classes also extend `RuntimeException`, for example `src/main/java/com/hospitalclaims/service/SearchQueryException.java:3-6`. |
| Polymorphism used | `Met` | Repositories implement the generic `CrudRepository<T, ID>` interface, giving multiple concrete implementations the same abstract contract: `src/main/java/com/hospitalclaims/repository/CrudRepository.java:7-12`, `src/main/java/com/hospitalclaims/repository/PatientRepository.java:14`, `src/main/java/com/hospitalclaims/repository/ClaimRepository.java:14`. The HTTP server also uses an `Action` interface with method references/lambdas for route handling in `src/main/java/com/hospitalclaims/HospitalClaimsHttpServer.java:90-112` and its functional interface declaration near the end of the class. |
| All class-wide variables are private to prevent content coupling | `Partially met` | Production code is strong here: for example `HospitalClaimsService` fields are `private final` in `src/main/java/com/hospitalclaims/service/HospitalClaimsService.java:28-34`, and model fields are private in `src/main/java/com/hospitalclaims/model/Patient.java:4-12`. However, test infrastructure exposes `protected` fields in `src/test/java/com/hospitalclaims/integration/MysqlIntegrationTestSupport.java:21-24`, so this is not true for the whole codebase. |
| Class-wide variables are kept to a minimum to ensure a minimum of common coupling | `Met` | Most classes only keep the dependencies they need, for example `HospitalClaimsService` stores repository collaborators only (`src/main/java/com/hospitalclaims/service/HospitalClaimsService.java:28-34`) and `ViewSearchService` stores only three fields (`src/main/java/com/hospitalclaims/service/ViewSearchService.java:24-26`). Static shared state is minimal, mainly constants such as `ValidationUtils.SIMPLE_EMAIL_PATTERN` (`src/main/java/com/hospitalclaims/service/ValidationUtils.java:6-8`) and HTTP formatting/page-size constants (`src/main/java/com/hospitalclaims/HospitalClaimsHttpServer.java:49-55`). |
| Data coupling is used (parameter passing) in preference to content or common coupling | `Met` | Methods communicate through parameters rather than reaching into other objects' internals. Good examples: `HospitalClaimsService.updateVisit(String, String, LocalDate, Visit)` in `src/main/java/com/hospitalclaims/service/HospitalClaimsService.java:126-140`, `ViewSearchService.search(...)` in `src/main/java/com/hospitalclaims/service/ViewSearchService.java:74-84`, and repository methods such as `PatientRepository.findById(String)` in `src/main/java/com/hospitalclaims/repository/PatientRepository.java:71-84`. |
| Program does not contain a lot of unnecessary data coupling | `Partially met` | In general the parameter passing is reasonable, but there are some broad method signatures that suggest extra coupling, for example `ViewSearchService.search(String, String, String, String, boolean, String, String)` in `src/main/java/com/hospitalclaims/service/ViewSearchService.java:74-80` and `HospitalClaimsService.updateVisit(String, String, LocalDate, Visit)` in `src/main/java/com/hospitalclaims/service/HospitalClaimsService.java:126-140`. This is acceptable, but not especially lean. |
| Classes are highly cohesive | `Partially met` | Many classes are cohesive: model classes only represent data (`src/main/java/com/hospitalclaims/model/Patient.java:3-100`), repositories focus on persistence (`src/main/java/com/hospitalclaims/repository/PatientRepository.java:14-137`), and `ValidationUtils` is focused on validation only (`src/main/java/com/hospitalclaims/service/ValidationUtils.java:6-47`). Cohesion is weaker in very large classes such as `HospitalClaimsHttpServer` and `ViewSearchService`, which each handle several responsibilities inside one file. |

## Strong examples to mention in a submission

- `HospitalClaimsService` is a strong example of constructor-based dependency injection, validation before persistence, and object collaboration: `src/main/java/com/hospitalclaims/service/HospitalClaimsService.java:36-50`, `52-203`.
- `RepositorySupport` plus repository implementations are strong examples of inheritance and polymorphism: `src/main/java/com/hospitalclaims/repository/RepositorySupport.java:8-20`, `src/main/java/com/hospitalclaims/repository/CrudRepository.java:7-12`, `src/main/java/com/hospitalclaims/repository/ClaimRepository.java:14-155`.
- `ViewSearchService` is a strong example of using multiple data structures and control structures to implement non-trivial logic: `src/main/java/com/hospitalclaims/service/ViewSearchService.java:24-31`, `87-127`, `164-220`.
- `AppEndToEndIntegrationTest` is a strong example that the implementation works across multiple linked classes and persistence layers: `src/test/java/com/hospitalclaims/integration/AppEndToEndIntegrationTest.java:28-201`.

## Main caveats

- The requirement that all class-wide variables are private is not fully true across the whole codebase because `MysqlIntegrationTestSupport` uses `protected` fields in test code.
- The requirement for high cohesion is only partly convincing because `HospitalClaimsHttpServer` and `ViewSearchService` are both large, multi-purpose classes.
- The requirement for comments throughout is only partly met because comments are minimal.
