# Diagram Descriptions

This file describes four UML-style diagrams in natural language for the current hospital claims application. The descriptions reflect the code in `src/main/java/com/hospitalclaims`.

## Class Diagram

The class diagram should be centered on `HospitalClaimsService` as the main orchestration class. It depends on seven repository classes: `ClaimRepository`, `InsuranceRepository`, `PatientRepository`, `DoctorRepository`, `DrugRepository`, `PrescriptionRepository`, and `VisitRepository`. Each repository encapsulates persistence for one aggregate or table, while `HospitalClaimsService` applies validation, referential checks, business rules, and workflow transitions before delegating to the repositories.

The core domain entities are `Patient`, `Doctor`, `Insurance`, `Drug`, `Prescription`, `Visit`, and `Claim`. A `Patient` optionally references one `Insurance` provider through `insuranceId` and optionally references one primary care `Doctor` through `primaryCareDoctorId`. A `Prescription` belongs to exactly one `Patient`, one prescribing `Doctor`, and one `Drug`. A `Visit` links one `Patient` and one `Doctor`, and is identified by a composite business key of patient ID, doctor ID, and visit date. A `Claim` is created from one `Prescription`, then derives its `patientId` and `insuranceId` from the linked prescription and patient record.

The service layer also exposes derived read models. `PrescriptionReview` wraps a `Prescription` together with the resolved `Drug`, resolved `Doctor`, a computed end date, an active flag, an eligibility flag, and a list of eligibility issues. `ClaimView` wraps a `Claim` together with its `PrescriptionReview`, so claim pages and reports reuse the same prescription-review logic. `PatientHistoryReport` aggregates one `Patient`, optional `Insurance`, optional primary care `Doctor`, a list of `Visit` records, and a list of `PrescriptionReview` records.

The browser search subsystem should appear beside the transactional service. `HospitalClaimsHttpServer` depends on both `HospitalClaimsService` and `ViewSearchService`, and also uses `SavedViewSearchStore` for persisted search presets. `ViewSearchService` transforms data from `HospitalClaimsService` into dataset-oriented search results using `ViewDataset`, `ViewQuery`, `ViewRecord`, `ViewSearchResult`, `ViewGroup`, and `ViewComposedSearchResult`. This part of the diagram should show that the HTTP server is the entry point for browser interactions, while `HospitalClaimsService` remains the source of business data and rules.

## Use Case Diagram

The use case diagram should show two main actors: an `Operations User` and a `Claims Reviewer`. If preferred, the browser and CLI can be treated as channels rather than actors, because both ultimately call the same service layer.

The `Operations User` participates in administrative and clinical record workflows: register insurance, register patient, register doctor, register drug, record visit, record prescription, update those records, delete records where allowed, search patients by surname, search doctors by specialization, search drugs by name, and view patient history. The same actor can also open the browser workspace and run dataset searches, grouped searches, composed cross-dataset searches, inline edits for supported datasets, and saved-search management.

The `Claims Reviewer` participates in the claims workflow: create claim draft, submit claim, move claim to under review, approve claim, reject claim, inspect the claim queue, and inspect prescription review issues that influence claim eligibility. The diagram should show `Create claim draft` including a lookup of the linked prescription and patient insurance, because that relationship is mandatory in the current implementation.

Several use cases include validation or rule checks. `Record prescription` includes checking that the patient, doctor, and drug exist and that there is no overlapping active prescription for the same patient and drug. `Create claim draft` includes ensuring the prescription exists and the patient has insurance. `Approve claim` and `Reject claim` both include a status guard that only allows claims already in `SUBMITTED` or `UNDER_REVIEW`.

## Activity Diagram

The activity diagram should model the end-to-end claim-processing path starting from a user choosing to create a claim. The first action is to enter `claimId`, `prescriptionId`, and optional notes. The system then validates that the claim ID and prescription ID are present, loads the prescription, loads the patient tied to that prescription, and checks whether the patient has an insurance ID. If the prescription is missing or the patient has no insurance, the flow ends in a validation failure.

If those checks pass, the system copies the patient ID and insurance ID into the new claim, assigns status `DRAFT`, sets `createdDate` to today, verifies there is not already a claim for the prescription, and saves the claim. The next activity is optional submission. When the user submits the claim, the system checks that the current state is `DRAFT`, changes the state to `SUBMITTED`, sets `submittedDate`, and saves the update.

From `SUBMITTED`, the flow can branch. One branch moves the claim into review: validate reviewer name, change status to `UNDER_REVIEW`, set `reviewedBy`, and persist. From either `SUBMITTED` directly or `UNDER_REVIEW`, the reviewer can approve or reject. Approval sets status `APPROVED`, stores `reviewedBy`, stores `decisionDate`, and stores optional decision notes. Rejection sets status `REJECTED`, stores `reviewedBy`, stores `decisionDate`, and requires non-blank decision notes before saving.

An attached decision node should also mention that claim pages and review pages use `PrescriptionReview` to compute contextual eligibility issues. That derived review checks for missing insurance, missing doctor, missing drug, absence of a supporting visit within 30 days before the prescription date, long-duration prescriptions without a clinical comment, and overlapping same-drug prescriptions. Those checks do not currently block claim creation or approval automatically, but they are part of the operational review flow shown in the UI and reports.

## State Diagram

The state diagram should model the lifecycle of `Claim.status`. The initial implemented state is `DRAFT`, created by `createClaim`. From `DRAFT`, the only implemented transition is `submitClaim`, which moves the claim to `SUBMITTED` and sets the submission date.

From `SUBMITTED`, two implemented transitions exist. `markClaimUnderReview` moves the claim to `UNDER_REVIEW` and records the reviewer. `approveClaim` can also move the claim directly from `SUBMITTED` to `APPROVED`, and `rejectClaim` can move it directly from `SUBMITTED` to `REJECTED`.

From `UNDER_REVIEW`, `approveClaim` transitions to `APPROVED`, and `rejectClaim` transitions to `REJECTED`. Both terminal decision states record `reviewedBy` and `decisionDate`, with rejection additionally requiring decision notes. No implemented transition returns a claim to an earlier state.

The enum also defines a `PAID` state, so it should appear in the diagram as a declared but currently unreachable state. The code validates `PAID` as a legal status string, but there is no service method that transitions a claim into `PAID`, and there are no transitions out of `APPROVED` or `REJECTED` beyond persistence and reporting.

## Browser Navigation And Action Flow Diagram

This diagram should be drawn as a hybrid page-flow map: each browser route is a node like a sitemap, but each node should also show the main user actions, the service outcomes they trigger, and the next page or same-page return path. The single top-level actor can be `Browser Operator`, with the browser interface entered through `/`, which functions as the dashboard and navigation hub.

The first node should be `/` Dashboard. It shows operational counts for insurance providers, patients, doctors, drugs, prescriptions, visits, and claims. From this page, the operator can navigate to five workflow pages: `/records`, `/claims`, `/reviews`, `/view`, and `/delete`. The dashboard itself does not mutate data; it is a control surface that fans out into the rest of the browser application.

The `/records` node should be split into two subareas inside the same page: `Create records` and `Update records`. `Create records` contains actions to register insurance, register patient, register doctor, register drug, record visit, and record prescription. `Update records` contains actions to update insurance, patient, doctor, drug, visit, and prescription. Every POST action on this page goes to a dedicated `/actions/...` endpoint and then redirects back to `/records` with either a success flash message or an error flash message. The diagram should show that the operator stays within the same page context after each create or update attempt, rather than moving to a separate confirmation page.

The `/claims` node should show both mutation actions and a read-only queue panel on the same page. The action cluster contains `Create claim draft`, `Submit claim`, `Move to under review`, `Approve claim`, and `Reject claim`. Each action posts to its own `/actions/...` route and redirects back to `/claims` with a success or error message. The queue panel displays all claims or a patient-filtered subset, so the page also has a self-looping `Queue filter` GET action that reloads `/claims?patientId=...`. The diagram should make clear that this page is both a workflow executor and the main queue-monitoring page for claim status progression.

The `/reviews` node should be modeled as one page with multiple query-driven panels selected by the `panel` parameter. Its query controls branch to `Patient history`, `Prescription review`, `Search patients`, `Search doctors`, and `Search drugs`, but each branch returns to the same `/reviews` route with different query parameters. The result area changes depending on the selected panel: patient history renders a full patient history report, prescription review renders eligibility-oriented prescription review rows, patient search returns matching patients, doctor search returns matching doctors, and drug search returns matching drugs. This should be shown as a same-page branching flow rather than five separate physical pages.

The `/view` node should be the most detailed branch in the diagram because it behaves like a generic data workspace. The primary flow begins with `Run search`, where the operator selects a dataset and optional query, sort, group, page size, and group-sort settings, then reloads `/view` with those parameters. From the resulting state, several secondary loops exist on the same page: `Save current search` posts to `/actions/save-view-search` and returns to `/view`; `Run saved search` reloads `/view?savedSearch=...`; `Delete saved search` posts to `/actions/delete-view-search` and returns to `/view`; `Previous page` and `Next page` reload `/view` with a different page number; and `Export CSV` or `Export JSON` branch to `/view/export` for downloadable output. The diagram should also show a drill-down path where clicking a composable cell value in the results table opens a composed cross-dataset search on `/view` using `composed`, `sourceDataset`, `sourceColumn`, and `value` parameters. That composed search still remains inside the View workspace rather than navigating to a different feature area.

Inside the `/view` branch, inline editing should appear as a conditional action loop for editable datasets only: `patients`, `doctors`, `drugs`, `visits`, and `prescriptions`. Selecting `Edit row` reveals an inline form, posting to `/actions/view-inline-edit`, which then redirects back to the same `/view` dataset, filter, grouping, page, and page-size state with a flash message. The diagram should explicitly mark `claims` and `claim-review` as read-only datasets in this workspace, because they display results and exports but do not support the inline edit loop.

The `/delete` node should be isolated visually from the routine operational pages to reflect the code and interface intent. It contains a single destructive-action form for deleting insurance, patient, doctor, drug, visit, prescription, or claim records. The flow should show a hard validation gate requiring the confirmation text `DELETE`, followed by a POST to `/actions/delete`, and then a redirect back to `/delete` with either a success or error message. A note on the diagram should show that dependent records must be removed first, so some delete attempts fail and loop back with validation feedback.

Across all browser pages, the diagram should show one repeated pattern on the action arrows: `GET page -> operator submits form or action -> POST /actions/... or GET with query params -> service validation/business logic -> redirect back to owning page with flash message or refreshed results`. That common pattern is the main reason this diagram sits between a sitemap and a use-case diagram: it shows both where the user can go and what each page does when used.
